# 02 · 화면 흐름과 상태 기계 — 확정본

> 이 문서는 **구현 계약**이다. `state.js` 구현자는 §5 하나로 파일을 쓸 수 있어야 하고,
> `ui.js` 구현자와 `court3d.js` 구현자는 §7 하나로 서로의 파일을 열어보지 않고 작업할 수 있어야 한다.
> 여기서 확정한 **엘리먼트 id·data-\* 속성·함수 시그니처는 협상 대상이 아니다.** 바꾸려면 이 문서를 먼저 고친다.
>
> 근거: `00-요구사항-원본.md` §3 / §6 / §8, `01-지문3-원문.md`.
> 표기 `[R§3]` 은 요구사항 원본의 해당 절을 가리킨다.

## 0. 한 장 요약

| 결정 | 값 |
|---|---|
| 화면 | `start` · `lobby` · `case` · `result` — **4개뿐** |
| 사건 화면의 위상 | `ask` → `lock` → `feedback` — 화면 전환이 아니라 **한 화면 안의 위상** |
| 피드백 | 사건 화면을 **떠나지 않고** 그 자리에 열린다. 자동으로 닫히지 않는다 [R§3] |
| '다음 사건' | 로비를 거치지 않고 **아직 완료되지 않은 다음 사건**으로 직행 [R§3] |
| 마지막 사건 | 피드백을 **먼저** 보여주고, 같은 버튼이 `결과 보기`로 바뀐다 [R§3] |
| 채점 | **최초 선택으로만.** 재방문·연타로 변하지 않는다 [R§3] |
| `완료 n/10` vs `정확도 x/10` | **다른 값, 다른 필드, 다른 화면.** 진행 중에는 완료만 보여준다 |
| 저장 | `localStorage` 키 `nz.progress` / `nz.prefs`, 값 안에 `v` |
| 저장 실패 | 메모리로 계속 굴러간다. 게임은 절대 멈추지 않는다 [R§6] |

## 1. 화면 목록

| 화면 | `data-screen` | 최상위 id | 역할 | 이탈 경로 |
|---|---|---|---|---|
| 시작 | `start` | `#nz-start` | 제목 + 시작 버튼 + 안내 한 줄. **철학 설명 금지** [R§3] | 시작 / 이어하기 / 처음부터 |
| 로비 | `lobby` | `#nz-lobby` | 3D 법정의 사건 파일 10개. 미열람·현재·완료 구분 [R§3] | 파일 선택 |
| 사건 | `case` | `#nz-case` | 상황 + 선택지 + (같은 자리에) 피드백 | 다음 사건 / 사건 목록 / 결과 보기 |
| 결과 | `result` | `#nz-result` | 정확도 + 두 질문 + 교사 연결 문구 | 사건 다시 보기 / 처음부터 |

**화면은 이 4개가 전부다.** 피드백을 다섯 번째 화면으로 만들지 마라.
사건 본문이 화면에서 사라지면 학생이 "내가 뭘 읽고 골랐더라"를 잃고, 피드백의 한 줄 이유가 공중에 뜬다.
피드백은 `#nz-case` 안에서 본문 **아래에 덧붙는다.**

### 시작 화면에 들어가는 것

```
노직의 철학 법정
내 생각 말고, 노직의 생각!

"네 생각을 고르는 게임이 아닙니다. 노직이라면 어떤 답을 고를지 맞혀 보세요."

              [ 법정 열기 ]
```
그 이상 쓰지 않는다. 원칙은 사건을 풀면서 알아차리게 한다 [R§3].

## 2. 전이표 (Transition Table)

`E:` 는 이벤트, `G:` 는 가드(거짓이면 이벤트를 **조용히 버린다**), `A:` 는 동작.

| # | 현재 | E: 이벤트 | G: 가드 | A: 동작 | 다음 |
|---|---|---|---|---|---|
| T1 | BOOT | 로드 완료 | 저장 없음 ∨ 손상 ∨ 무의미 | `reset({silent:true})` | START(기본) |
| T2 | BOOT | 로드 완료 | 유효 ∧ 의미 있음(§6.4) | 스냅샷 보관, 아직 적용 안 함 | START(이어하기) |
| T3 | START(기본) | `#nz-btn-start` | — | `startFresh()` · `setScreen('lobby')` | LOBBY |
| T4 | START(이어하기) | `#nz-btn-resume` | — | `resume()` → 저장된 `screen`/`phase` 복원 | 저장된 화면 |
| T5 | START(이어하기) | `#nz-btn-fresh` | — | `reset()` · `startFresh()` (패널 자체가 확인 절차, §6.5) | LOBBY |
| T6 | LOBBY | 파일 활성화 | `caseId` 가 DATA에 존재 | `setCurrent(id)` · `setScreen('case')` · `setPhase(isAnswered(id) ? 'feedback' : 'ask')` | CASE |
| T7 | CASE·ask | 선택지 활성화 | `phase==='ask'` ∧ armed(§4.2) ∧ `!busy` | `answer(cur, choiceId)` · `setPhase('lock')` · `Court.react()` | CASE·lock |
| T8 | CASE·ask | `Esc` / `#nz-btn-lobby` | — | `setScreen('lobby')` — **미응답 사건은 `unread` 그대로** | LOBBY |
| T9 | CASE·lock | 반응 종료(타이머) ∨ 모션 감소 | — | `markDone(cur)` · `setPhase('feedback')` · 버튼 arm | CASE·feedback |
| T10 | CASE·feedback | `#nz-btn-next` | `!allDone()` | `id=nextUnanswered(cur)` · `setCurrent(id)` · `setPhase(isAnswered(id)?'feedback':'ask')` | CASE |
| T11 | CASE·feedback | `#nz-btn-next` | `allDone()` | `setScreen('result')` | RESULT |
| T12 | CASE·feedback | `#nz-btn-lobby` / `Esc` | — | `markDone(cur)`(멱등) · `setScreen('lobby')` | LOBBY |
| T13 | LOBBY | 완료된 파일 활성화 | `isDone(id)` | T6과 동일. `#nz-case[data-review="true"]` 추가 | CASE·feedback |
| T14 | RESULT | `#nz-btn-result-lobby` | — | `setScreen('lobby')` | LOBBY |
| T15 | RESULT | `#nz-btn-agree-yes/no` | — | `setAgree('yes'\|'no')` — **채점 없음, 화면 유지** [R§3] | RESULT |
| T16 | LOBBY ∨ CASE ∨ RESULT | `#nz-btn-restart` | — | 확인 모달 열기, 포커스 저장 | (모달) |
| T17 | 모달 | `#nz-btn-confirm-yes` | — | `reset()` · `setScreen('start')` | START(기본) |
| T18 | 모달 | `#nz-btn-confirm-no` / `Esc` | — | 모달 닫기 · 포커스 복귀 | 원래 화면 |

### 전이 규칙 3개

1. **T10이 이 게임의 심장이다.** `다음 사건`은 로비를 거치지 않는다 [R§3].
   `nextUnanswered`는 **DATA 배열 순서로 현재 사건 다음부터 순환 탐색**하고 `done`이 아닌 첫 사건을 준다.
   7번을 먼저 열었으면 8·9·10 → 1·2… 순으로 돈다. 사건은 전부 독립적이므로 순서는 문제되지 않는다 [R§3].
2. **T9는 자동 전이지만 T10/T11은 절대 자동이 아니다.** 피드백은 학생이 버튼을 누를 때까지 남는다 [R§3].
   타이머로 피드백을 닫는 코드를 쓰지 마라.
3. **T11의 버튼은 T10과 같은 엘리먼트다.** 새 버튼을 만들지 않는다 —
   `#nz-btn-next` 의 `data-action` 이 `next` ↔ `result` 로 바뀌고 라벨만 갈린다.
   그래야 마지막 사건에서 학생의 손가락이 이미 있던 자리에서 결과로 넘어간다.

## 3. 상태 객체 스키마

### 3.1 저장되는 형태 (localStorage `nz.progress` 의 값)

```json
{
  "v": 1,
  "startedAt": 1757836800000,
  "savedAt": 1757836912345,
  "elapsedMs": 84210,
  "firstChoice": {
    "case01": "case01_o2",
    "case02": "case02_o1",
    "case07": "case07_o1"
  },
  "done": ["case01", "case02"],
  "current": "case07",
  "phase": "feedback",
  "screen": "case",
  "agree": null
}
```

| 필드 | 타입 | 의미 | 불변성 |
|---|---|---|---|
| `v` | `1` | 스키마 버전. 불일치 = 폐기(§6.3) | — |
| `startedAt` | `number` (ms epoch) | **최초** 시작 시각. `resume()`은 이 값을 건드리지 않는다 | `reset()` 전까지 불변 |
| `savedAt` | `number` | 마지막 저장 시각. 이어하기 패널의 기본 포커스 결정(§6.4) | 매 저장 갱신 |
| `elapsedMs` | `number` | **누적 플레이 시간.** 탭을 닫은 시간은 포함하지 않는다(§3.4) | 단조 증가 |
| `firstChoice` | `{[caseId]: choiceId}` | **사건별 최초 선택. 한 번 쓰이면 절대 안 바뀐다.** 채점의 유일한 근거 | **쓰기 1회** |
| `done` | `caseId[]` | **피드백까지 확인한 사건.** 오답도 포함된다 [R§3] | 추가만, 제거 없음 |
| `current` | `caseId \| null` | 마지막으로 연 사건. 복구 지점 | 가변 |
| `phase` | `"ask" \| "lock" \| "feedback"` | 사건 화면의 위상. `screen!=='case'`면 무의미 | 가변 |
| `screen` | `"lobby" \| "case" \| "result"` | 복구할 화면. **`"start"`는 저장하지 않는다** | 가변 |
| `agree` | `"yes" \| "no" \| null` | 결과 화면의 선택 설문. **채점 대상 아님** [R§3] | 1회 기록 |

**`feedbackOpen`은 `phase === 'feedback'` 과 동의어다.** 두 개의 진실을 두지 않기 위해 별도 불리언을 저장하지 않고,
`NZ.State.feedbackOpen()` 은 `phase==='feedback'` 을 반환하는 파생 접근자로 제공한다(§5).
`setFeedbackOpen(true/false)` 도 `setPhase('feedback'/'ask')` 로 위임한다.
**이유:** 예전 설계에서 `feedbackOpen=true` 인데 `phase==='ask'` 인 상태가 실제로 만들어졌고,
그 상태에서 선택지가 다시 눌려 두 번째 채점이 시도됐다. 파생값으로 만들면 그 상태가 **표현 불가능**해진다.

### 3.2 저장하지 않는 파생값 — 계산해서 쓴다

| 값 | 계산 | 왜 저장하지 않나 |
|---|---|---|
| `completedCount()` | `done.length` | 저장하면 `done`과 어긋난다 |
| `score()` | `done` 중 `firstChoice[id] === DATA.byId[id].answerId` 인 개수 | 저장하면 재방문 시 부풀릴 여지가 생긴다 |
| `answeredCount()` | `Object.keys(firstChoice).length` | 파생 |
| `allDone()` | `done.length === DATA.cases.length` | 파생 |
| `stateOf(id)` | `done` ∋ → `done` / `firstChoice` ∋ → `answered` / 아니면 `unread` | 파생 |

> **`완료 7/10` 과 `첫 선택 정답 4개` 는 서로 다른 값이다** [R§3].
> `completedCount()` 의 분모는 10, `score()` 의 분모도 10이지만 **분자가 세는 집합이 다르다.**
> 전자는 `done`, 후자는 `done ∩ (최초 선택이 노직의 답과 일치)`.
> 화면에서도 절대 같은 줄에 붙여 쓰지 않는다.

### 3.3 `score()` 의 정의를 `done` 기준으로 못 박는 이유

`score()` 는 `firstChoice` 전체가 아니라 **`done` 에 속한 사건만** 센다.

답만 하고(=`firstChoice` 기록됨) 피드백 표시 직전에 탭이 죽으면 `firstChoice` ⊋ `done` 인 상태가 잠깐 존재한다.
이때 `firstChoice` 기준으로 세면 **정확도 5 / 완료 4** 같은 화면이 물리적으로 가능해진다.
`done` 기준으로 고정하면 `score() ≤ completedCount()` 가 **항상** 참이고, 그 화면은 만들 수 없다.

잃는 것은 없다 — `markDone()` 은 피드백이 **읽히는 순간**(반응 애니메이션 종료 시점) 호출되므로(§4.3)
그 창은 1초 미만이고, 복구 시 그 사건은 `phase='feedback'` 으로 되살아나 즉시 `done` 이 된다(§6.6).

### 3.4 경과 시간 — `startedAt` 하나로 계산하지 않는다

```js
// state.js 내부
var anchor = Date.now();                 // 이번 세션이 시작된 시각
function flushClock() {                  // save() 맨 위에서 호출
  var now = Date.now();
  st.elapsedMs += (now - anchor);
  anchor = now;
}
function elapsedMs() { return st.elapsedMs + (Date.now() - anchor); }
```

`Date.now() - startedAt` 로 계산하면, 4교시에 시작하고 6교시에 이어한 학생의 결과 화면에 **`2시간 13분`** 이 뜬다.
누적 방식은 탭이 닫혀 있던 시간을 건너뛴다. `visibilitychange`(hidden) 와 `pagehide` 에서 `save()` 를 한 번 더 호출한다.

시간은 **경과 시간만** 표시하고 카운트다운을 쓰지 않는다. 5분이 지나도 아무 일도 일어나지 않는다 [R§3].
`#nz-hud-clock` 은 `mm:ss`, 색·굵기 변화 없음, 5:00을 넘겨도 경고 스타일로 바뀌지 않는다.

### 3.5 별도 키: `nz.prefs`

```json
{ "v": 1, "muted": true, "motion": null }
```

| 필드 | 기본값 | 비고 |
|---|---|---|
| `muted` | `true` | 효과음 기본 OFF [R§5] |
| `motion` | `null` | `null`=OS 설정 따름, `"reduced"`/`"full"`=사용자 수동 지정 |

**진행 기록과 분리한 이유:** `전체 다시 시작` 이 음소거를 풀어버리면 안 된다.
교실 한복판에서 소리가 켜지는 사고가 난다. `reset()` 은 `nz.progress` 만 지운다.

## 4. 채점 규칙과 입력 잠금

### 4.1 채점 3원칙

1. **최초 선택으로만 계산한다.** `firstChoice[caseId]` 는 쓰기 1회. 이후 어떤 경로로도 덮어쓰이지 않는다 [R§3].
2. **정답 판정은 ID로 한다.** `firstChoice[id] === DATA.byId[id].answerId`.
   화면의 A/B는 **렌더 위치가 만드는 라벨**이고 채점과 무관하다 [R§4].
3. **`정답`이라는 단어를 상태·API·화면 어디에도 쓰지 않는다.** 필드명은 `match`.
   반환값도 `match: true|false`. 화면 문구는 `노직의 판단과 일치 / 불일치`.
   **작품의 내레이션이 노직을 절대적 정답으로 선언하면 안 되기 때문이다** [R§5, 지문문서 "절대 하지 말 것"].
   변수명에서부터 막아두면 나중에 누가 `"정답입니다!"` 를 타이핑할 확률이 줄어든다.

### 4.2 선택지 ID 규약과 순서 섞기

```js
// data.js — 채점이 위치에 묶이지 않게 하는 유일한 방법
{ id: 'case01',
  choices: [ { id: 'case01_o1', text: '노력하지 않았으니…' },
             { id: 'case01_o2', text: '정당한 재산을 자발적으로…' } ],
  answerId: 'case01_o2' }
```

- 선택지 ID는 `<caseId>_o1` / `<caseId>_o2` — **원고 작성 순서**를 뜻할 뿐, 화면의 A/B와 무관하다.
- 화면 라벨 `A`/`B` 는 렌더 시점에 위치로 붙인다: `#nz-choice-1` → A, `#nz-choice-2` → B.
- **기본값은 섞지 않는다(고정 순서).** 이유 둘:
  (a) 교사 진행안·원고와 화면이 일치해야 수업 중 구두 안내가 가능하다.
  (b) 섞으려면 **셔플 시드를 저장에 넣어야 한다** — 안 그러면 완료 사건 재방문 시 내가 고른 항목이
  다른 자리에 있어 "내가 저걸 골랐나?" 가 된다. 시드는 스키마 `v:2` 의 일이다. 지금은 넣지 않는다.
- 섞기를 켜더라도 §4.1-2 때문에 채점은 바뀌지 않는다. 회귀 테스트로 고정한다(§8).

### 4.3 입력 잠금 — 네 겹

> [R§3] "답을 고르면 즉시 입력을 잠가 더블클릭·연타에 의한 중복 채점을 막는다."

| 겹 | 위치 | 막는 것 |
|---|---|---|
| ① 동기 플래그 | `ui.js` `busy` | 같은 틱·연속 틱의 두 번째 `click` |
| ② 무장 지연 `ARM_MS=150` | `ui.js` | **`다음 사건` 더블클릭의 두 번째 클릭이 다음 사건의 선택지에 떨어지는 것** |
| ③ 위상 가드 | `ui.js` `State.phase()!=='ask'` | 피드백 중에 날아온 키 입력 |
| ④ 상태 레벨 단일화 | `state.js` `answer()` | ①②③이 전부 뚫려도 **채점은 절대 두 번 되지 않는다** |

```js
/* ---- ui.js : 선택지 잠금 ---------------------------------------------- */
var ARM_MS = 150;
var armAt  = 0;        // performance.now() 기준. 이 시각 전의 입력은 버린다
var busy   = false;

function armChoices() {                        // 사건이 열릴 때 / T10 직후
  busy  = false;
  armAt = performance.now() + ARM_MS;
  for (var i = 0; i < choiceBtns.length; i++) choiceBtns[i].disabled = true;
  setTimeout(function () {
    if (NZ.State.phase() !== 'ask') return;    // 그 사이 위상이 바뀌었으면 풀지 않는다
    for (var i = 0; i < choiceBtns.length; i++) choiceBtns[i].disabled = false;
  }, ARM_MS);
}

function onChoiceClick(ev) {
  if (busy) return;                                       // ①
  if (performance.now() < armAt) return;                  // ②
  if (NZ.State.phase() !== 'ask') return;                 // ③
  busy = true;                                            // 동기적으로, 즉시
  caseEl.dataset.phase = 'lock';                          // CSS pointer-events:none
  for (var i = 0; i < choiceBtns.length; i++) choiceBtns[i].disabled = true;

  var r = NZ.State.answer(NZ.State.current(),             // ④
                          ev.currentTarget.dataset.choiceId);
  if (!r.accepted) { renderFeedback(); return; }          // 이미 답한 사건 → 기존 결과를 그린다
  NZ.bus.emit('case:answer', r);
  var ms = NZ.Court.react(r.match ? 'match' : 'miss', NZ.State.current());
  setTimeout(toFeedback, ms);                             // T9
}
```

구현 세부 규칙:

- **`click` 만 바인딩한다.** `pointerdown` + `click` 을 같이 걸면 터치에서 두 번 발화한다.
- **키보드는 `keydown` + `if (e.repeat) return;`.** Enter 를 누르고 있으면 반복 이벤트가 쏟아진다.
- **`disabled = true` 를 반드시 쓴다.** `pointer-events:none` 만으로는 키보드 활성화를 못 막는다.
- **`dblclick` 은 바인딩하지 않는다.** 더블클릭은 `click` 2회로 오고, ①이 두 번째를 먹는다.
- **`#nz-btn-next` 에도 같은 `busy`/arm 을 적용한다.** 연타로 두 사건을 건너뛰는 사고를 막는다.
- **선택지와 `다음 사건` 버튼은 같은 화면 좌표를 공유하지 않는다.** ②가 최후 방어선이지 유일한 방어선이면 안 된다.

### 4.4 `answer()` 의 멱등성

```js
answer('case03', 'case03_o1')  // → {accepted:true,  choiceId:'case03_o1', match:true,  expectedId:'case03_o1', reason:null}
answer('case03', 'case03_o2')  // → {accepted:false, choiceId:'case03_o1', match:true,  expectedId:'case03_o1', reason:'already'}
```

두 번째 호출은 **기록을 건드리지 않고 기존 결과를 그대로 반환한다.** 던지지 않는다(throw 금지).
UI는 `accepted:false` 를 받으면 "이미 답한 사건"으로 알고 피드백을 다시 그리면 된다 —
이게 **완료 사건 재방문(T13)과 연타 방어가 같은 코드 경로를 쓰게 되는 지점**이고, 그래서 버그가 한 군데에만 생긴다.

`state.js` 는 **DOM을 모른다.** `document` 를 단 한 번도 참조하지 않는다.

### 5.3 구현자가 반드시 지킬 것

```js
// 1. answer() 는 쓰기 1회. hasOwnProperty 로 막는다. (falsy 값 걱정은 없지만 습관이 맞다)
if (Object.prototype.hasOwnProperty.call(st.firstChoice, caseId)) {
  return { accepted:false, choiceId: st.firstChoice[caseId],
           match: st.firstChoice[caseId] === expected, expectedId: expected, reason:'already' };
}

// 2. markDone 은 firstChoice 없이는 통과 못 한다. done ⊆ keys(firstChoice) 불변식의 유일한 관문.
if (!Object.prototype.hasOwnProperty.call(st.firstChoice, caseId)) return false;

// 3. onChange 는 복사본을 순회한다. 콜백 안에서 자기 자신을 해제하면
//    splice 때문에 다음 구독자가 건너뛰어진다. (SR2 트롤리에서 실제로 났던 버그다.)
var list = subs.slice();
for (var i = 0; i < list.length; i++) { try { list[i].fn(snapshot()); } catch (e) {} }

// 4. 저장은 try/catch 로 감싸고, 실패해도 게임은 계속된다. [R§6]
function save() {
  flushClock(); st.savedAt = Date.now();
  try { localStorage.setItem(KEY, JSON.stringify(st)); return true; }
  catch (e) { if (storageOkFlag) { storageOkFlag = false; NZ.bus.emit('storage:fail'); } return false; }
}
```

### 5.4 불변식 — 테스트로 고정한다

| # | 불변식 | 깨지면 생기는 화면 |
|---|---|---|
| I1 | `done ⊆ keys(firstChoice)` | 답 안 한 사건이 완료로 잡힘 |
| I2 | `0 ≤ score() ≤ completedCount() ≤ 10` | `정확도 5 / 완료 4` |
| I3 | `firstChoice[id]` 는 `reset()` 전까지 불변 | 재방문으로 점수 변동 |
| I4 | `nextUnanswered(x) === null ⟺ allDone()` | 결과로 못 가거나, 남았는데 결과로 감 |
| I5 | `screen==='result' ⇒ allDone()` | 미완료 상태의 결과 화면 |
| I6 | 같은 사건을 n번 열어도 `completedCount()`·`score()` 변화 0 | [R§8] 점수 부풀리기 |
| I7 | `elapsedMs()` 단조 증가 ∧ ≥ 0 | 음수 시간 |
| I8 | 모든 `answerId` 가 그 사건의 `choices[].id` 안에 존재 | 영원히 못 맞히는 사건 [R§8] |

## 6. 저장 · 복구 · 초기화

### 6.1 키

| 키 | 값 | 수명 |
|---|---|---|
| `nz.progress` | §3.1 JSON | `reset()` 까지 |
| `nz.prefs` | §3.5 JSON | 영구 (reset 무관) |

**접두사 `nz.` 는 필수다.** 배포 주소가 `totojunior.github.io/MSH/SR2/NZ/` 이므로
1차시 트롤리(`trolley.*`)·2차시 출생추첨과 **origin 이 같고 localStorage 를 공유한다.**
접두사가 없으면 앞 차시 자료의 키를 덮어써 2차시 수업을 망가뜨린다.
버전은 키 이름이 아니라 **값 안의 `v`** 에 둔다 — 키에 버전을 박으면 구버전 데이터가 지워지지 않고 영원히 남는다.

### 6.2 저장 시점

| 시점 | 호출 |
|---|---|
| `answer()` 성공 | 즉시 |
| `markDone()` 변경 | 즉시 |
| `setCurrent` / `setScreen` / `setPhase` / `setAgree` | 즉시 |
| `visibilitychange` → hidden, `pagehide` | 즉시 (`flushClock` 목적) |
| 매 프레임 / 타이머 | **금지.** 경과 시간은 `startedAt`+`elapsedMs` 로 파생되지 저장으로 누적하지 않는다 |

세션당 쓰기 횟수는 40회 남짓, 페이로드는 400바이트 미만이다. 디바운스가 필요 없다.

### 6.3 스키마 불일치 처리 — `sanitize(raw)`

`sanitize` 는 `{state, repaired}` 를 반환한다. `repaired===true` 면 승격 직후 한 번 저장해 고쳐진 형태를 굳힌다.

| 상황 | 처리 |
|---|---|
| 키 없음 | `null` → fresh |
| `JSON.parse` 실패 | 키 삭제 → fresh |
| `v` 없음 ∨ `v !== 1` | **폐기.** 키 삭제 → fresh (v1이므로 마이그레이션 없음) |
| 최상위가 객체가 아님 / `firstChoice` 가 객체 아님 / `done` 이 배열 아님 | 폐기 → fresh |
| `done`·`firstChoice` 에 DATA에 없는 `caseId` | **그 항목만 제거**, 나머지 유지, `repaired=true` |
| `firstChoice[id]` 가 그 사건의 `choices[].id` 에 없음 | 그 항목 제거 + `done` 에서도 제거, `repaired=true` |
| `done` 에 중복 | 중복 제거, `repaired=true` |
| `current` 가 DATA에 없음 | `current=null`, `screen='lobby'`, `repaired=true` |
| `screen` 이 미지의 값 | `'lobby'` |
| `screen==='start'` | `'lobby'` (시작 화면은 저장 대상이 아니다) |
| `screen==='result'` 인데 `!allDone()` | `'lobby'` — I5 |
| `phase==='lock'` | **`'feedback'` 으로 승격** (§6.6) |
| `phase` 가 미지의 값 | `'ask'` |
| `startedAt` 이 숫자 아님 | `Date.now()` |
| `elapsedMs` 가 숫자 아님 ∨ 음수 ∨ `> 24h` | `0` |
| `agree` 가 `'yes'/'no'/null` 아님 | `null` |

> **DATA 대조 검증이 진짜로 필요한 이유:** README에 "사건은 데이터 파일에서 고친다"고 쓸 것이고 [R§6],
> 교사가 실제로 선택지 문구나 ID를 고친 뒤 학생 크롬북에 남아 있던 옛 저장이 로드된다.
> 대조하지 않으면 **존재하지 않는 선택지 ID가 채점기에 들어가 영원히 불일치로 뜨는** 사건이 생긴다.

### 6.4 '의미 있는 진행' 판정과 이어하기 UX

```js
function meaningful(s) {
  return s && (s.done.length > 0 || Object.keys(s.firstChoice).length > 0 || s.screen === 'result');
}
```

로비까지만 갔다가 새로고침한 경우는 **묻지 않고 그냥 새로 시작한다.** 도입 5분짜리 활동의 첫 10초에
"이어하시겠습니까?" 를 띄워서 고2에게 결정을 시킬 이유가 없다.

의미 있는 진행이 있으면 시작 화면 안에 분기 패널 `#nz-resume` 이 열린다.

```
   노직의 철학 법정

   진행 중인 기록이 있습니다 — 완료 4/10
   ┌────────────────────┐  ┌──────────────────────────┐
   │   이어하기          │  │ 처음부터 (기록 4개 삭제)  │
   └────────────────────┘  └──────────────────────────┘
```

- **기본 포커스:** `savedAt` 이 2시간 이내면 `#nz-btn-resume`, 아니면 `#nz-btn-fresh`.
  (`STALE_MS = 2*60*60*1000`) 공용 크롬북에서 **다른 반 학생의 기록**을 이어받는 사고를 줄인다.
- `#nz-btn-start` 는 이 패널이 열려 있는 동안 숨긴다. 버튼 3개를 나란히 두지 않는다.
- `storageOk()===false` 면 `#nz-storage-note` 를 시작 화면에만 한 줄 띄운다:
  *"이 브라우저에서는 진행 상황이 저장되지 않습니다. 새로고침하면 처음부터 시작합니다."*
  게임 중에는 다시 띄우지 않는다.

### 6.5 전체 다시 시작 — 2단계 확인 [R§6]

`#nz-btn-restart`(헤더, 게임 중) → `#nz-confirm` 모달:

```
   기록을 지우고 처음부터 시작할까요?
   완료 7/10 과 지금까지의 선택이 모두 사라집니다.

   [ 취소 ]   [ 지우고 처음부터 ]
```

- `window.confirm()` 을 쓰지 않는다. 렌더 루프를 멈추고, 브라우저가 억제할 수 있고, 한국어 줄바꿈이 깨진다.
- **기본 포커스는 `#nz-btn-confirm-no`(취소).** 파괴적 동작을 Enter 한 번에 두지 않는다.
- `Esc` = 취소. 모달을 열기 전 포커스를 저장했다가 닫을 때 되돌린다.
- 모달이 열려 있는 동안 배경 화면의 포커스 가능 요소는 `tabindex="-1"` 로 빼거나 `aria-hidden` 처리한다.
- §6.4의 `처음부터` 버튼은 **이 모달을 띄우지 않는다.** 그 버튼의 라벨 자체가
  `처음부터 (기록 4개 삭제)` 로 잃는 것을 명시하고 있고, 그 화면은 이미 2지 선택이므로 그것이 확인 절차다.

### 6.6 새로고침 복구 매트릭스

| 새로고침 시점 | 저장된 값 | 이어하기 후 화면 | `firstChoice` | `done` | 점수 |
|---|---|---|---|---|---|
| 시작 화면(미시작) | 없음 | 시작 화면 (분기 없음) | — | — | — |
| 로비, 아직 0개 | 무의미 판정 | 시작 화면 (분기 없음), 기록 폐기 | — | — | — |
| 로비, 3개 완료 | `screen:lobby` | 로비. 파일 3개 `done` | 3 | 3 | 유지 |
| 사건 문제 화면(미선택) | `screen:case, phase:ask` | **그 사건의 문제 화면 그대로.** 선택 미기록 | 변화 없음 | 변화 없음 | 유지 |
| 선택 직후 반응 중 | `screen:case, phase:lock` | **`feedback` 으로 승격.** 반응 애니메이션은 재생하지 않고 피드백을 바로 보여준다 | 이미 기록됨 | 로드 직후 `markDone` | 유지 |
| 피드백 화면 | `screen:case, phase:feedback` | 같은 피드백 그대로 | 기록됨 | 기록됨 | 유지 |
| 결과 화면 | `screen:result` | 결과 화면 (`allDone` 재확인 후) | 10 | 10 | 유지 |
| 확인 모달이 열린 채 | 모달은 저장하지 않음 | 모달 없이 배경 화면 | 유지 | 유지 | 유지 |

`lock → feedback` 승격 시 애니메이션을 다시 재생하지 않는 이유: 새로고침은 되감기가 아니다.
학생이 원하는 건 "아까 그 답이 맞았나"이지 도장 찍는 장면의 재생이 아니다.

### 6.7 완료한 사건 재방문 [R§6]

| 항목 | 동작 |
|---|---|
| 진입 위상 | `feedback` 으로 바로 연다. 문제를 다시 풀리지 않는다 |
| 선택지 | 화면에 남되 `disabled`, 내가 고른 쪽에 `data-picked="true"`, 노직의 답에 `data-expected="true"` |
| 마크업 | `#nz-case[data-review="true"]` — CSS가 "다시 보기" 배지를 붙인다 |
| 노직 반응 | **재생하지 않는다.** `NZ.Court.setPose(match?'approve':'object')` 로 정지 포즈만 |
| 점수 | 변화 0. `answer()` 는 호출조차 하지 않는다 |
| 다음 버튼 | `allDone()` 이면 `결과 보기`, 아니면 `다음 사건` — 미완료 사건으로 정확히 간다 |

## 7. DOM 구조 계약

### 7.1 소유권 — 이 표가 두 구현자의 경계다

| 영역 | 소유자 | 다른 쪽이 할 수 있는 것 |
|---|---|---|
| `#nz-gl` (canvas) | **court3d.js 전용** | ui.js는 읽지도 쓰지도 않는다 |
| `#nz-root` 이하 전부 | **ui.js 전용** | court3d.js는 `document.querySelector` 를 쓰지 않는다 |
| `#nz-root` 의 `data-*` | ui.js가 쓴다 | court3d.js는 **읽지 않는다** — `NZ.bus` 로 받는다 |
| 상태 | state.js | 양쪽 다 읽기만. 쓰기는 ui.js만 |

**두 모듈은 서로의 DOM을 절대 만지지 않는다.** 통신은 `NZ.bus` 와 `NZ.Court.*` 호출뿐이다.
그래서 3D가 없어도(WebGL 실패) ui.js가 그대로 돌고, ui.js를 다시 써도 court3d.js가 안 깨진다.

### 7.4 data-\* 속성 규약

| 속성 | 위치 | 값 | 쓰는 쪽 |
|---|---|---|---|
| `data-screen` | `#nz-root` | `start` `lobby` `case` `result` | ui.js |
| `data-three` | `#nz-root` | `on` `off` | ui.js (court3d 초기화 결과를 받아) |
| `data-motion` | `#nz-root` | `full` `reduced` | ui.js |
| `data-sound` | `#nz-root` | `on` `off` | ui.js |
| `data-case-id` | `#nz-case`, `.nz-file` | `case01`…`case10` | ui.js |
| `data-phase` | `#nz-case` | `ask` `lock` `feedback` | ui.js |
| `data-review` | `#nz-case` | `true` `false` | ui.js |
| `data-state` | `.nz-file` | `unread` `answered` `done` | ui.js |
| `data-current` | `.nz-file` | `true` `false` | ui.js |
| `data-choice-id` | `.nz-choice` | `case01_o1` 등 | ui.js |
| `data-label` | `.nz-choice` | `A` `B` (렌더 위치가 결정) | ui.js |
| `data-picked` | `.nz-choice` | `true` `false` — 피드백 위상에서만 의미 | ui.js |
| `data-expected` | `.nz-choice` | `true` `false` — 노직의 예상 답 | ui.js |
| `data-verdict` | `#nz-fb-verdict` | `match` `miss` | ui.js |
| `data-action` | `#nz-btn-next` | `next` `result` | ui.js |
| `data-key` | `mark.nz-key` | `holdings` `transfer` `fraud` `consent` `force` | ui.js (데이터가 지정) |

**규칙 3개**

1. **`data-screen` 이 화면 전환의 유일한 스위치다.** ui.js는 `style.display` 를 쓰지 않는다.
   비활성 화면에는 `hidden` 도 함께 건다 — `hidden` 이라야 포커스와 스크린리더에서 완전히 빠진다.
   진입 애니메이션은 `hidden` 을 벗긴 **다음 프레임**에 `.is-in` 클래스를 붙여 건다. 퇴장 애니메이션은 쓰지 않는다.
2. **색으로만 구분하지 않는다** [R§6]. `data-verdict` 는 아이콘(도장 / 지휘봉 자국)과
   `일치 / 불일치` 라는 **글자**를 함께 바꾼다. `data-state` 도 `미열람 / 진행 중 / 완료` 배지 글자를 바꾼다.
3. **`data-*` 는 상태의 거울일 뿐 상태가 아니다.** 진실은 `NZ.State` 에만 있다.
   `dataset` 을 읽어서 분기하는 로직을 쓰지 마라 — 단, 클릭 핸들러가 `currentTarget.dataset.caseId` 를
   식별자로 읽는 것은 허용한다(그건 상태가 아니라 주소다).

### 7.5 court3d.js ↔ ui.js 인터페이스

```js
/* court3d.js 가 노출하는 것 — 이게 전부다 */
window.NZ.Court = {
  /** @returns {boolean} false 면 WebGL 불가. ui.js 가 data-three="off" 로 2D 대체 */
  init: function (canvasEl) {},

  /** 화면에 맞는 카메라/조명 프리셋. 이동 조작·탐색 없음 [R§5] */
  setScene: function (screen) {},                 // 'start'|'lobby'|'case'|'result'

  /** 로비 파일 10개의 겉모습. ui.js 가 State 를 보고 만들어 넘긴다 */
  setFiles: function (list) {},                   // [{id, state:'unread'|'answered'|'done', current:boolean}]

  /** 포커스/호버 중인 파일 강조. null 이면 해제 */
  highlightFile: function (caseId) {},

  /** 반응 재생. @returns {number} 이 반응이 끝나는 데 걸리는 ms (600~1200, 모션 감소면 0) */
  react: function (kind, caseId) {},              // 'match' | 'miss'

  /** 애니메이션 없이 정지 포즈만 (완료 사건 재방문 / lock→feedback 승격 복구) */
  setPose: function (kind) {},                    // 'idle' | 'approve' | 'object'

  /** 대기 자세로 */
  idle: function () {},

  /** 모션 감소 반영 */
  setReducedMotion: function (on) {}
};
```

- **`react()` 의 반환값이 T9의 타이머 길이다.** ui.js가 자체 상수를 두지 않는다 —
  애니메이션 길이를 아는 쪽은 3D다. 모션 감소면 `0` 을 반환하고 ui.js는 `setTimeout(fn, 0)` 로 즉시 넘어간다.
- **`react()` 실패나 3D 부재 시에도 반드시 숫자를 반환해야 한다.** (`data-three="off"` 면 스텁이 `0` 반환)
  반환값이 `undefined` 면 `setTimeout(fn, undefined)` 가 되어 피드백이 안 열리는 게 아니라
  **즉시 열려버려 반응 연출이 통째로 사라진다.** 스텁을 반드시 둔다.
- **로비 파일의 입력은 DOM 버튼이 유일한 권한이다.** 3D 파일 오브젝트는 그림이다.
  three.js 레이캐스트로 클릭을 받으면 키보드 선택[R§6]과 포커스 표시를 다시 만들어야 하고,
  둘이 어긋나면 "클릭은 되는데 탭으로는 못 여는 사건"이 생긴다.
  court3d.js 는 앵커 좌표만 알려주고, ui.js 가 그 위에 투명 버튼을 얹는다:

```js
// court3d.js → 로비에서 카메라가 움직였거나 리사이즈됐을 때만 (매 프레임 아님)
window.dispatchEvent(new CustomEvent('nz:anchors', {
  detail: { anchors: [ { id:'case01', x:412, y:288, scale:1.0, visible:true }, /* … */ ] }
}));
// x,y = CSS 픽셀, 캔버스 좌상단 기준
```

`data-three="off"` 면 `nz:anchors` 는 발생하지 않고, CSS가 `#nz-file-list` 를 평범한 2열 그리드로 떨어뜨린다.
**그 상태에서도 10개 사건을 전부 풀 수 있어야 한다** [R§6].

### 7.6 `NZ.bus` — 12줄짜리 이벤트 버스 (state.js 에 둔다)

```js
NZ.bus = (function () {
  var m = {};
  return {
    on:   function (n, fn) { (m[n] = m[n] || []).push(fn);
                             return function () { var i = m[n].indexOf(fn); if (i >= 0) m[n].splice(i, 1); }; },
    emit: function (n, p)  { var l = (m[n] || []).slice();
                             for (var i = 0; i < l.length; i++) { try { l[i](p); } catch (e) {} } }
  };
})();
```

| 이벤트 | 페이로드 | 발신 | 수신 |
|---|---|---|---|
| `screen` | `{from, to}` | ui.js | court3d.js(`setScene`), sfx.js |
| `case:open` | `{caseId, review}` | ui.js | court3d.js, sfx.js |
| `case:answer` | `AnswerResult` | ui.js | sfx.js |
| `case:feedback` | `{caseId, match}` | ui.js | sfx.js |
| `state:change` | `Snapshot` | state.js | ui.js |
| `storage:fail` | — | state.js | ui.js (1회) |
| `reset` | — | state.js | 전부 |

`court3d.js` 가 `NZ.State` 를 **직접 읽는 것은 허용**한다(읽기 전용). 쓰기는 금지.

### 8.1 응답 조합 [R§8]

| 시나리오 | firstChoice | done | `score()` | 결과 화면 도달 | 확인 포인트 |
|---|---|---|---|---|---|
| 전부 일치 | 10 | 10 | 10 | ✓ | `정확도 10/10`. "완벽" 류 과장 문구 금지 |
| 전부 불일치 | 10 | 10 | 0 | ✓ | **결과에 도달해야 한다.** 맞힐 때까지 반복 금지 [R§3]. `롤스가 좋아합니다` 류 문구 금지 [R§3] |
| 혼합 4/10 | 10 | 10 | 4 | ✓ | `완료 10/10` 과 `정확도 4/10` 이 서로 다른 줄에 뜬다 |
| 9개 완료 + 1개 미열람 | 9 | 9 | ≤9 | ✗ | `다음 사건` 이 그 1개로 간다. `결과 보기` 는 나타나지 않는다 |
| 9개 완료 + 1개 답만 함 | 10 | 9 | ≤9 | ✗ | 그 사건을 열면 `feedback` 으로 열리고 즉시 `done`. 그 다음 `결과 보기` |
| 마지막 사건 | 10 | 10 | — | ✓ | **피드백이 먼저 뜨고** 같은 버튼이 `결과 보기` 로 바뀐다. 반응 생략 금지 [R§3] |
| 7번부터 시작 | — | — | — | — | 7→8→9→10→1→2… 순환. 1번을 안 읽어도 이해된다 [R§3] |
| 로비에서 무작위 순서 | — | — | — | ✓ | `nextUnanswered` 는 항상 `done` 아닌 것만 준다. 이미 푼 사건으로 되돌아가지 않는다 |

### 8.2 입력·조작

| 상황 | 동작 |
|---|---|
| 선택지 더블클릭 | 1회만 채점. 두 번째 `click` 은 `busy` 가 먹는다 |
| 선택지 연타 10회 | 1회만 채점. `answer()` 가 `accepted:false` 반환 |
| 두 선택지를 거의 동시에 | 먼저 도착한 `click` 만. JS는 단일 스레드라 `busy=true` 가 그 사이에 이미 서 있다 |
| `다음 사건` 더블클릭 | 1개만 전진. 두 번째 클릭은 `ARM_MS` 창에 걸려 버려진다 |

| 사건 화면에서 `Esc` | `ask` → 로비(기록 없음) / `feedback` → 로비(완료 유지) |
| 결과 화면에서 동의 버튼 2회 | 마지막 선택으로 갱신. 채점 영향 0 [R§3] |

### 8.3 환경

| 상황 | 동작 |
|---|---|
| WebGL 불가 / 3D 초기화 실패 | `data-three="off"`. 2D 배경 + DOM 사건 진행. **10개 전부 풀 수 있다** [R§6] |
| localStorage 차단(시크릿·정책) | 메모리 상태로 정상 플레이. 시작 화면에 안내 1줄. 새로고침하면 처음부터 |

| `nz.progress` 를 devtools에서 손상 | `sanitize` 폐기 → 시작 화면. **콘솔 에러 0** |
| 데이터 파일에서 사건 ID 변경 후 옛 저장 로드 | 그 항목만 제거(§6.3). 나머지 진행은 유지 |

| 모션 감소 ON | `react()` → `0ms`. 위상 전이는 동일. 상태 기계 변화 없음 |
| 1366×768 / 좁은 화면 | 화면 구조 불변. `#nz-case-body`·`.nz-choice` 는 줄바꿈으로 흐른다. 잘림 금지 [R§6] |

## 9. 다른 모듈에 거는 최소 계약

`state.js` 가 `NZ.DATA` 에서 실제로 읽는 것은 이것뿐이다. **데이터 파일 담당자는 이 세 가지만 보장하면 된다.**

```js
NZ.DATA = {
  v: 1,
  cases: [
    { id: 'case01',                                  // 필수 · 고유 · 순서가 곧 사건 순서
      choices: [ { id: 'case01_o1', /* … */ },       // 필수 · 고유 · 정확히 2개
                 { id: 'case01_o2', /* … */ } ],
      answerId: 'case01_o2' }                        // 필수 · choices[].id 중 하나여야 함
    /* … 10개 … */
  ]
};
NZ.DATA.byId = /* state.js 가 부팅 시 만든다 */;
```

부팅 시 `state.js` 가 다음을 검증하고, 실패하면 **콘솔에 경고하고 그 사건을 빼지 않고 그대로 둔다**
(수업 중 사건이 사라지는 것이 잘못 채점되는 것보다 나쁘다). 대신 자동 테스트가 이걸 잡는다(§5.4 I8).

- 사건 수 = 10, id 중복 없음
- 사건마다 `choices.length === 2`, choice id 중복 없음
- `answerId` 가 그 사건의 `choices[].id` 에 존재

### 모듈 로드 순서 (assemble)

```
data.js  →  state.js (NZ.bus 포함)  →  sfx.js  →  court3d.js  →  ui.js  →  main.js
```

`main.js` 가 하는 일은 3줄이다: `State.init()` → `Court.init()` 결과로 `data-three` → `UI.start()`.

## 10. 시간 예산 [R§3]

| 구간 | 목표 | 상태 기계상 근거 |
|---|---|---|
| 시작 화면 | ~10초 | 버튼 1개. 이어하기가 있으면 +3초 |
| 사건 1개 | 20~25초 | 읽기 12~15초 + 선택 2초 + 반응 0.6~1.2초 + 피드백 읽기 6~8초 |
| × 10 | 200~250초 | `다음 사건`이 로비를 건너뛰므로 사건당 클릭 **2회**(선택 1 + 다음 1) |
| 결과 | ~20초 | 동의 설문은 선택이고 건너뛸 수 있다 |
| 합계 | **약 4분 30초 ~ 5분** | 실제 학생 읽기 속도로 검증한 값이 아니다. **"약 5분 목표로 설계"라고만 쓴다** [R§8] |

로비를 매번 거치면 사건당 클릭이 3회, 화면 전환이 4회가 되어 **90초 이상 늘어난다.**
T10이 요구사항인 이유가 이것이다.

| 항목 | 규칙 |
|---|---|
| 포커스 이동 | 화면 전환 시 해당 `.nz-screen`(`tabindex="-1"`)에 포커스. 단 **피드백이 열릴 때는 `#nz-btn-next`** — Enter 연타로 흐름이 이어져야 한다 |
| 판정 안내 | `#nz-alert` 에 `노직의 판단과 일치 — 노직의 예상 답 B` 를 넣어 assertive 로 읽힌다 |
| 진행 안내 | `#nz-live` 에 `완료 7/10` |
| 키보드 · 로비 | `↑↓←→` 로 파일 이동(roving tabindex), `Enter`/`Space` 열기, 숫자키 직접 열기 |
| 키보드 · 사건 | `A`/`1`/`←` = 첫 번째 선택지, `B`/`2`/`→` = 두 번째, `Enter` = 다음, `Esc` = 목록 |
| 포커스 표시 | `:focus-visible` 에 2px 이상 윤곽선. 3D 배경 위에서도 대비가 보장되는 색 |
| 색 의존 금지 | §7.4 규칙 2 |
| 모션 감소 | `data-motion="reduced"` → 반응 0ms, 화면 전환 페이드만, 카메라 이동·흔들림 없음 |

## 12. 구현 체크리스트

- [ ] `state.js` 가 `document` 를 한 번도 참조하지 않는다
- [ ] `answer()` 를 같은 사건에 100번 호출해도 `score()`·`completedCount()` 불변
- [ ] `localStorage` 를 throw 하도록 스텁하고 10개 사건을 끝까지 플레이할 수 있다
- [ ] `nz.progress` 에 `{"v":99}` 를 넣고 새로고침 → 콘솔 에러 없이 시작 화면
- [ ] `phase:"lock"` 으로 저장된 상태를 넣고 새로고침 → 피드백 화면 + 해당 사건 `done`
- [ ] 전부 불일치로 10개를 끝내고 결과 화면에 도달한다
- [ ] 마지막 사건에서 피드백이 먼저 뜨고, 그 다음 버튼이 `결과 보기`다
- [ ] `data-three="off"` 를 강제하고 10개 사건을 전부 푼다
- [ ] 1366×768 에서 가로 스크롤 0, 잘린 글자 0
- [ ] `처음부터` → 확인 → 초기화 후에도 음소거 설정이 유지된다
- [ ] §5.4 불변식 I1~I8 을 콘솔에서 확인할 수 있는 `NZ.State.__invariants()` 를 개발 중에만 둔다
